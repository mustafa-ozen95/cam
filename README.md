# Camera panel (cam)

**English** · [Türkçe](README.tr.md)

Live view, playback and download for NVR/DVR/IP cameras; role/permission-based
membership, API keys, audit log. **Node.js 22+, no dependencies**, requires
ffmpeg. Interface in Turkish (default) / English.

| Type | Device | Protocol | Recording list |
|---|---|---|---|
| `uniview` | Uniview NVR (e.g. NVR302-32S) | LAPI (HTTP Digest) + RTSP, H.265 | per-day "has recording" → 15-min slices |
| `hikvision` | Hikvision NVR (e.g. DS-7616NI-Q2) | ISAPI (HTTP Digest) + RTSP, H.264 | real recording ranges → 15-min slices; camera registration on the NVR from the panel |
| `xiongmai` | Xiongmai / NetSurveillance DVR-NVR | DVR-IP (TCP 34567) | the device's file list |
| `camera` | Single IP camera (Hikvision/Dahua/Uniview/custom RTSP) | RTSP | live only |

## Installation
`docker-compose.yml` follows the Compose standard (compose-spec.io). Settings come from the environment (`.env.example`).
Data lives in MariaDB (`db` service, named volume `cam_database`); to use an external database set `DB_HOST` and the credentials and
`DB_REPLICAS=0` so the `db` service does not start. The HTTP port is not published; the reverse proxy in front provides the domain and TLS (it reaches the
panel on 80). The `/live` video comes from the `cam-rtc` (mediamtx) service over 8189/udp; the server address given to the
browser is `CAM_RTC_HOST`.
```
cp .env.example .env          # optional; chmod 600 .env
docker compose up -d --build  # or: npm start
cp docker-compose.override.example.yml docker-compose.override.yml   # without a proxy: panel directly on CAM_EXTERNAL_PORT (1165)
# second installation from the same source: separate folder + separate .env (CAM_CONTAINER, CAM_RTC_CONTAINER, CAM_DB_CONTAINER, CAM_DATA_VOLUME, CAM_DB_VOLUME, CAM_RTC_PORT, CAM_COOKIE); data is not shared
npm test                      # unit + integration (fake device; needs a MariaDB, see "Database and backup")
node scripts/openapi.mjs      # regenerate the OpenAPI document from the routes
```
On first start `admin` is created (if `CAM_ADMIN_PASSWORD` is not set, the password is in `data/initial-admin.txt`). Devices are added
from the **Cihaz** (device) tab (the connection is tested before saving); `CAM_DEVICES` is only the initial seed while
the `devices` table is empty.

## Database and backup
All data (members, devices, roles, API keys, audit log, channel settings, /live layout, update status, KYM links) is in MariaDB/MySQL
(driver `mysql2`, utf8mb4). Connection: `DB_HOST` (default `db`), `DB_PORT` (3306), `DB_DATABASE` (`cam`), `DB_USERNAME` (`cam`),
`DB_PASSWORD` (required). At start the panel waits for the database (`DB_WAIT_SEC`, default 60 s) and then runs its own migrations
(version table `migrations`, ordered, repeating does nothing). `/api/v1/health` is unhealthy when the database is unreachable.
- Tables: `users`, `devices`, `roles`, `builtin_role_permissions`, `api_keys`, `hub_links`, `audit_log` (one row per entry; the signature chain is kept and verified from the database), `settings` (name → JSON), `migrations`.
- The **secret key** is never stored in the database (a dump must not sit next to the encrypted device passwords): `CAM_SECRET_KEY` (base64, 32 bytes; `openssl rand -base64 32`); if empty, `data/secret.key` is used (generated with mode 0600 when missing). If the variable differs from that file, or from the key that filled the database, start-up stops with a clear message. Keep the key together with the backups.
- **Backup = a database dump** (e.g. `docker compose exec db sh -c 'mariadb-dump --single-transaction -u"$MARIADB_USER" -p"$MARIADB_PASSWORD" "$MARIADB_DATABASE"' > cam.sql`) plus the secret key.
- **Cryptographic labels** (`src/core/crypto-labels.mjs`): session `cam/session`, KYM flow `cam/hub-flow`, API key hashes `cam/api-key`, device password key `cam/device-password`, audit chain `cam/audit-log`, key fingerprint `cam/key-fingerprint`. Changing a label invalidates what it protects; stored data (device passwords, audit chain, fingerprint) moves with a migration. Migration 3 moved from the previous labels: it re-encrypts device passwords, re-signs the audit chain after verifying it (a broken chain or a wrong key stops start-up), and **revokes all active API keys once** (only a one-way hash is stored, so they cannot be moved; create new ones). Sessions and sign-in flow cookies from before it stop working.

## Permissions and API
- Permission catalog, DC roles (admin, network, technical, accounting) and custom roles, camera **scope** (device/channel list), account expiry, IP/CIDR list.
- **API key** (`kp_…`, only the digest is stored, shown once; rate limit, concurrent streams, IP list, expiry, revoke, rotate).
- Privilege escalation is blocked: nobody can grant a permission/scope they do not have; nor can they touch an **existing** member (the password, role or deletion of a member more privileged than them or outside their scope), account constraints (expiry, IP list, rate/stream limit) cannot be handed on more loosely than one's own, and a person cannot lift their own restriction.
- An API key derives from its owner: if the owner is deleted / expires / is outside the IP list / loses access in KYM, the key stops working too, and its permissions never exceed the owner's **current** role; when a member is deleted their keys are revoked. A key without a member owner (integration-labelled, granted through permission.manage) works with its own rights. Ownership is determined by the `owner` field, not by the key's display name.
- Camera scope is also enforced on write operations (channel settings, device edit/delete/clock); someone with a scope cannot add devices or delete recordings. `/api/info` returns no channel/device data outside the scope. Channel numbers are PERMANENT (`settings` · `device-block-limit`): a deleted device's block is never given to a new device, so numeric channel scopes do not shift onto a new device.
- Documentation: `/docs/api-v1.tr.md`, `/docs/api-v1.en.md`, `/docs/openapi.json` (**requires a session**).

## Sign-in with the Identity Management Center (KYM)
The same flow as the DC panels (Authorization Code + PKCE): the user signs in on the center's page, the password never reaches this panel. A client is created in the center (Yönetim → Uygulamalar); the redirect address must be `https://<domain>/login/hub/callback`, and **which roles may enter is chosen in the center**. When all four variables are set, a "… ile giriş" (sign in with …) button appears on the sign-in page; local username + password sign-in always remains (so the panel stays reachable while the center is down).

```
CAM_HUB_URL=https://dc.ornek.test          CAM_HUB_CLIENT_ID=<client id>
CAM_HUB_CLIENT_SECRET=<client secret>                   CAM_HUB_REDIRECT_URI=https://kamera.ornek.test/login/hub/callback
CAM_HUB_NOTIFY_SECRET=<notification secret>    CAM_HUB_NAME="Kimlik Yönetim Merkezi"
CAM_HUB_ROLE_MAP='{}'                         CAM_HUB_DEFAULT_ROLE=           CAM_HUB_CHECK_MINUTES=5
```
- **Roles are the same as in the DC panels:** `admin` (everything, immutable), `network`, `technical`, `accounting` (born without permissions; their permissions are granted under Yetki → Roller, name/identity fixed). A role in the center maps to the role of the same name; a different mapping via `CAM_HUB_ROLE_MAP`, a role without a counterpart via `CAM_HUB_DEFAULT_ROLE` (if empty, no account is created). Custom roles can be added too.
- On first sign-in, if the center says "an account may be created", a member is created (name from the local part of the e-mail, random password). The link lives in the `hub_links` table; it is bound to the member **itself, not to their name** (creation stamp, `userStamp`): when the member is deleted the link is deleted, and a new member created with the same name cannot inherit the old identity. Old (unstamped) links are stamped onto the existing member at start-up; those without a member are dropped.
- Someone whose access is removed or whose role changes in the center changes here too: the center notifies immediately via `POST /api/identity/refresh` (HMAC signed); in addition `/api/identity-status` is asked every `CAM_HUB_CHECK_MINUTES` minutes. If the center cannot be reached, the last known state remains in force.
- Behind a reverse proxy (Caddy/nginx) set `CAM_IP_HEADER=X-Real-IP`; cookies are then `Secure` and HSTS is on (turned off with `CAM_PROXY=0`).

## Security
Only what the sign-in page needs is reachable without identity: the sign-in form, `css/js/font/icon`, `POST /api/login|logout`, the KYM sign-in flow and `/api/identity/refresh` (HMAC signed). **The API documentation (`/docs`) and `/api/v1` require a session**; `/api/v1/health` answers only from the container's own `127.0.0.1` address (HEALTHCHECK) and carries no details; `.json`/`.md` are never served from the static endpoint. The session cookie is bound to the member's creation stamp and session version: **signing out or changing the password invalidates all of that member's cookies**; signing purposes (session, KYM flow) are labelled separately. The per-IP sign-in limit (20 failures per minute → 60 s) is applied before the password hash is computed, and the hash is asynchronous; behind a reverse proxy without `CAM_IP_HEADER` this limit applies to the proxy's address. If a device's address/port changes, the password must be entered again (a stored password only goes to the target it was entered for).
Passwords use scrypt; device passwords AES-256-GCM; keys an HMAC digest; cookies HttpOnly+SameSite (Secure over HTTPS); CSRF header; CSP/nosniff/frame/referrer headers; 1 MB body limit; path traversal protection; brute-force lockout (sign-in and keys); no secrets in the log; HMAC-chained audit log. Behind a reverse proxy without `CAM_IP_HEADER` (e.g. `CF-Connecting-IP`), IP lists work on the socket address. Put TLS in front of plain HTTP.

## Environment variables
`CAM_PORT` (8191; 80 in the image), `CAM_HOST`, `CAM_TITLE`, `CAM_COOKIE` (several panels on the same IP: different names), `CAM_DATA` (data folder), `DB_HOST`, `DB_PORT`, `DB_DATABASE`, `DB_USERNAME`, `DB_PASSWORD`, `DB_WAIT_SEC`, `CAM_SECRET_KEY`, `CAM_DEVICES` (initial seed, JSON), `CAM_ADMIN_PASSWORD`, `CAM_RATIO` (16:9), `CAM_PLAYBACK_MAX` (4), `CAM_DOWNLOAD_MAX` (2), `CAM_STREAM_MAX` (24 per device), `CAM_FFMPEG`, `CAM_IP_HEADER`, `CAM_PROXY`, `CAM_TLS_CERT/KEY/PORT`, `CAM_LIVE_EMBED` (origins allowed to embed `/live`), `CAM_LIVE_DEFAULT` (`/live` cameras while no layout is saved: comma-separated channel numbers from 1, in order; empty = first 12), `CAM_HUB_*` (above), `UPDATE_TOKEN`, `UPDATE_HOOK_URL` (below), `CAM_TEST=1` (fake driver, tests only).

## Update check
**Güncelleme** (update) in the top menu (`update.check` permission; admin has it) compares the running version with the **last successful image build** of the main branch on GitHub: how many commits behind, which commits are new. The direction is measured as well; if the running version is newer than the last build it is not called an "update". The check runs by itself every morning at 06:50, the button runs it immediately; if a new version exists, those with this permission see a warning at the top of the page. If a new version exists and `UPDATE_HOOK_URL` (the platform's deploy hook, e.g. NineDeploy → Service → Settings → Deploy hook) is set, **Şimdi güncelle** (`update.apply` permission; admin has it) triggers that hook after a confirmation: the platform redeploys the repository's main branch. The panel cannot run anything on the server; the hook URL is a secret and never reaches the browser or the log. Same rules as Settings → Güncelleme in the DC panels.
- The running version is written into the image at build time (`ARG VERSION` → `APP_VERSION`; the workflow provides the commit). When the build does not pass the commit it is read from `.git` in the build context (`docker/read-version.sh`; `.dockerignore` lets in only `HEAD` and the refs). The result is stored in the database (`settings`, `update-status`).
- The repository is public: no token is needed, GitHub is asked anonymously (limit: 60 requests per hour per IP). For a private repository `UPDATE_TOKEN` must be a read-only token (fine-grained, panel repositories only, Contents and Actions: read).
- If the panel cannot reach GitHub (closed network), the check says "erişilemedi" (unreachable).

## Database (move or connect)
**Veritabanı** in the top menu (`database.manage` permission; admin has it) shows where the panel's database is and moves it to a remote server or connects a new installation to an existing one. Same flow as Settings → Veritabanı in the DC panels: test first, then confirm by typing the database name.
- **Taşı** (move) copies the current database into an EMPTY target and compares table/row counts on both sides.
- **Bağlan** (connect) does not copy: the new installation opens the old installation's database. The target must be this panel's (its migrations table), not newer than this version, and filled with the same secret key (`CAM_SECRET_KEY` or `data/secret.key`; checked against the stored key fingerprint).
- The work happens at startup, before the panel listens: the panel leaves a request in `data/database` and exits, the container restarts (`restart: unless-stopped`). If the first start on the remote database fails the panel returns to the environment's database (nothing was written there); once the move is complete it never falls back.
- The connection is stored in `data/database/connection.json`, encrypted with a key derived from the panel's secret key, and overrides `DB_*`.

## Language
Interface strings are written in Turkish; the dictionary and rules in `resources/views/web/js/lang.js` translate them to EN (the choice is made from the account menu in the top bar and stored in the browser). When adding a new string, add its English to the dictionary; write a rule (regex) for dynamic text. Role/permission names come from the server as `{tr, en}`.

## Design (identical to EYS)
The inner screens use the EYS panel's design template **unchanged**: top bar, account menu, column strip (live, recordings, three-pane device), admin tables, dialogs, notifications and theme are drawn with the same markup and the same CSS.
- `resources/views/web/css/eys/` and `resources/views/web/js/eys/` are **copies from EYS and are never edited by hand.** When EYS changes they are copied again with `node scripts/eys-sync.mjs <EYS checkout>` (`--check` only reports the difference); file digests are in `css/eys/OZET.json`, and `test/eys-design.test.mjs` catches manual edits.
- `css/app.css` imports only `fonts.css` (local fonts), `eys/app.css` and `camera.css`.
- `css/camera.css` **only adds**: camera-specific parts (grid, player, timeline, recording row, full screen). It never redefines a selector defined by EYS (a test checks); if needed a new modifier such as `.detail--genis` is added.
- `js/split.js`: on narrow screens it drops into the right pane (the EYS `columns.js` rule, because the selection lives in page state, not in the address).
